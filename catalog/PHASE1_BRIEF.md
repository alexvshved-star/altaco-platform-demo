# ALTACO · Фаза 1 — Сайт-каталог

## ТЗ + acceptance-чекліст для автономної сесії Claude Code

**Версія:** 1.0 · 10.06.2026 · Вхідний контракт: `altaco_materials.json` v1.0.0-rc2 (заморозити як v1.0.0 перед стартом)
**Принцип:** агент працює автономно; людина контролює входи (цей документ + контракт + дизайн-токени) і виходи (чекліст нижче). Зміна схеми даних під час сесії заборонена.

-----

## 0. Продуктова рамка: ALTACO Marketplace

Фаза 1 — не окремий сайт, а **перший публічний read-only шар платформи ALTACO Marketplace** над єдиним ядром даних. Цільова модель платформи: публічний каталог → онлайн-склад (партії, залишки, статуси) → консультант і КП-агент → адмінка → multi-brand/multi-supplier розширення. Канон послідовності — презентація платформи: Фаза 2 = Консультант + КП; склад, адмінка, аналітика — з пулу «за межами MVP», пріоритезуються реальними даними клієнтів.

**Правило сумісності з майбутнім:** заборонені технічні рішення, що унеможливлюють або суттєво ускладнюють майбутні онлайн-склад, адмінку, ролі, КП-генерацію, AI-консультанта, підключення backend. Конкретно:

- Доступ до даних — окремий шар (`src/lib/catalog.ts`), компоненти не читають JSON напряму. Завтра цей шар підміняється на API без переписування UI.
- Фільтри й секції генеруються з даних, не хардкодяться. Тест: матеріал нової лінії в JSON → нова секція без зміни коду (так «Головинський лабрадорит» з’явиться сам, коли з’являться дані — порожніх полиць у Фазі 1 не робимо).
- Каталог підтримує групування за лініями як публічні блоки: Bagnara Selection, Bagnara Kitchen Selection, SANTAMARGHERITA, Made in Italy, Marmo Elite — структура з поля `line`/`collection`.
- slab groups, партії, статуси, qty — основа майбутнього онлайн-складу: зберігаються в моделі повністю, навіть якщо публічно не показуються. «Не показуємо» ≠ «зайві поля».
- /catalog.json — публічна проєкція контракту, не заміна внутрішнього ядра.

**Противага (не менш обов’язкова):** сумісність з майбутнім = відсутність блокерів, НЕ присутність заготовок. Заборонено: системи ролей, скелети адмінки, незадіяні абстракції, конфіги «на виріст». Кожна ідея про склад/адмінку/КП/резервування — рядок у DECISIONS.md розділ «Backlog / Marketplace», не код.

## 1. Що будуємо

Публічний read-only шар платформи (див. §0): статичний каталог над `altaco_materials.json` у фірмовому стилі ALTACO. Дві сторінки-типи:

**Каталог** (як у макеті презентації, стор. 8): сітка карток з фото, назвою, типом/лінією, ціною «€ X / м²» або «€ X / slab», бейджем наявності. Фільтри: тип каменю, лінія/колекція, колір, фініш, товщина, наявність у Києві. Лічильник «N матеріалів». Сортування за ціною.

**Картка матеріалу** (макет, стор. 9): велике фото, хлібні крихти, назва, опис, таблиця характеристик (походження, колір, фініші, товщини, розмір сляба), теги застосувань, ціна з приміткою «Ціни в євро · з ПДВ · розрахунок у грн за курсом на день оплати», кнопки «Запросити КП» і «Додати в запит» (поки що — mailto/Telegram-лінк, без бекенду).

**Поза скоупом Фази 1:** консультант, генератор КП, кошик, оплата, особистий кабінет, CMS. Будь-яке «а давай заодно» — у беклог, не в код.

## 2. Дані — закон

- Єдине джерело: `data/altaco_materials.json`. Жодних захардкоджених матеріалів, цін чи назв у компонентах.
- Білд **падає**, якщо JSON не проходить `altaco_materials.schema.json`.
- Рендеряться картки зі статусом `published`. На час локальної розробки дозволено показ `draft` з плейсхолдером фото (генерований патерн з назвою — НЕ стокові фото каменю, щоб не брехати про матеріал). Перемикач `SHOW_DRAFTS` живе в конфігу; у production build — завжди `false`. Draft-позиції ніколи не потрапляють у production sitemap, /catalog.json, /llms.txt, JSON-LD чи інші публічні артефакти.
- `hidden` не рендериться ніколи й не потрапляє в білд-артефакти.
- Кілька slab_groups → одна картка з варіантами (фініш/товщина/партія), ціна на картці в сітці — «від €min».
- Фото — за конвенцією PHOTO_GUIDE.md: `photos/{id}/slab.jpg` + `detail-1.jpg` (+`detail-2.jpg`). Сітка каталогу показує detail-1 (текстуру), картка — повний сляб. Білд знаходить фото за id, поле `photos` у JSON не редагується вручну.
- `qty_slabs` ніколи не потрапляє в жоден публічний build-артефакт: HTML, DOM, JS-бандли, hydration payload, JSON-LD, meta, sitemap, /catalog.json, /llms.txt, assets чи sourcemaps. Дозволений лише узагальнений бейдж «В наявності · Київ» / «Під замовлення». Точна наявність — справа менеджера (примітка з прайсу).

## 3. Стек і структура

Рекомендовано: **Astro + Tailwind**, статичний експорт (хостинг = будь-який static, Netlify вже знайомий по NEURICA). Допустима заміна на Next.js static export, якщо агент обґрунтує в DECISIONS.md. TypeScript обов’язково; типи генеруються зі схеми (json-schema-to-typescript).

```
altaco-catalog/
  CLAUDE.md                  ← правила для агента
  data/altaco_materials.json + схема
  src/ (pages, components, lib)
  scripts/validate-data.mjs  ← schema + integrity (ціни, площі)
  catalog.public.schema.json ← схема публічного /catalog.json
  tests/                     ← Playwright smoke
  DECISIONS.md             ← агент веде журнал рішень
```

## 4. Дизайн-токени (підтвердити з Ігорем перед стартом)

- Фон сторінок: слонова кістка ≈ `#F1EEE7`; темні блоки/хедер: глибокий синьо-чорний ≈ `#131A24`
- Акцент: латунне золото ≈ `#B9985A` (ціни, лейбли, активні фільтри)
- Заголовки: serif (стиль макетів — Playfair Display або аналог з кирилицею); текст: гуманістичний sans (Inter/Manrope)
- Розріджені КАПС-лейбли з letter-spacing — як у прайсі й презентації
- Мова: UA. Структура i18n-ready (ключі, не хардкод), EN/RU — наступні фази.

## 5. SEO та агентська видимість

**Для Google (класика):**

- URL: `/katalog/{id}` латиницею (id вже slug-чисті), canonical, sitemap.xml, robots.txt.
- Title/meta за шаблоном з даних: «{Назва} — {тип} {колір} | купити сляб у Києві | ALTACO», description з характеристик. Без генерованих маркетингових текстів.
- Семантика: одна h1 на сторінку, характеристики як `<dl>`/`<table>`, alt фото з даних («{Назва}, {фініш}, сляб {розмір}»).
- **JSON-LD Schema.org на кожній картці:** `Product` + `Offer` (price, priceCurrency EUR, availability InStock/PreOrder з даних, brand за лінією) + `BreadcrumbList`. На головній — `LocalBusiness` (ALTACO, вул. Будіндустрії 7, Київ, телефон, графік). JSON-LD генерується з контракту, не пишеться руками — ціна в розмітці фізично не може розійтися з ціною на сторінці.
- hreflang-структура закладена (UA зараз, EN/RU потім).

**Для AI-агентів (GEO):**

- `/llms.txt` у корені: хто такий ALTACO, що на сайті, лінк на машинний фід.
- **Публічний фід `/catalog.json`** — проєкція контракту: тільки published, БЕЗ qty_slabs, todo_manual, notes_internal, hidden-позицій. Окрема схема `catalog.public.schema.json`, валідація в білді. Це той самий фід, який у Фазі 2 їстиме консультант — зовнішні агенти (ChatGPT, Perplexity, Claude з пошуком) отримують його ж.
- Контент-відповіді на сторінках: характеристики текстом у DOM (не canvas/js-only), щоб краулери агентів читали без рендерингу.
- У `robots.txt` НЕ блокувати GPTBot/ClaudeBot/PerplexityBot — видимість в агентських відповідях це канал продажів, а не загроза.

**Додаток до acceptance-чеклісту (автоматичні):**

- [ ] JSON-LD кожної картки проходить локальну структурну валідацію: присутні Product, Offer, BreadcrumbList; priceCurrency === “EUR”; ціна в JSON-LD === ціна в DOM === ціна в контракті; availability відповідає даним; draft/hidden відсутні в production JSON-LD
- [ ] `/catalog.json` валідний проти публічної схеми; grep-тест: жодного входження `qty_slabs`, `notes_internal`, `todo_manual`, hidden-id
- [ ] `/llms.txt` існує і посилається на живий фід
- [ ] Сторінки рендеряться без JS (SSG) — `curl` сторінки містить назву, ціну, характеристики

## 6. Acceptance-чекліст (агент проганяє сам перед фіналом)

**Автоматичні (CI-able):**

- [ ] `npm run validate` — JSON валідний проти схеми, інтегрітні перевірки (€/slab ≈ €/м² × площа, ≤5%) зелені
- [ ] Білд без errors і без warnings від власних validation/type/build-скриптів; warnings сторонніх інструментів агент фіксує в DECISIONS.md з оцінкою, чи це блокер
- [ ] Негативний тест окремою командою `npm run test:negative-data`: працює з fixture/тимчасовою копією JSON, реальний data/altaco_materials.json не змінюється; білд на зламаній копії падає
- [ ] Playwright: каталог рендерить рівно стільки карток, скільки published(+draft при SHOW_DRAFTS) у JSON — число з даних, не з фікстури
- [ ] Кожен фільтр звужує видачу; комбінація фільтрів = перетин; «скинути» повертає все
- [ ] Marketplace-ready тест: тимчасове додавання тестового матеріалу нової лінії в копію JSON створює нову секцію/фільтр без зміни коду; компоненти не імпортують JSON напряму (grep: import.*altaco_materials лише в src/lib/)
- [ ] Кожна картка-сторінка відкривається за `/katalog/{id}`, 404 для hidden і неіснуючих id
- [ ] Ціни рендеряться через єдину функцію форматування, що бере значення з контракту; тест порівнює очікуваний відформатований рядок з DOM: у сітці — «від €min», на картці — фактичні retail-ціни груп
- [ ] Grep-тест по всьому dist/: жодного входження `qty_slabs`, `notes_internal`, `todo_manual` у жодному build-артефакті (включно з JS і sourcemaps)
- [ ] Lighthouse (mobile): Performance ≥ 90, A11y ≥ 90, SEO ≥ 90
- [ ] Валідні `<title>`/meta/OG на всіх сторінках; sitemap.xml; кирилиця в URL відсутня

**Ручні (Олександр, ~15 хв):**

- [ ] Візуальна відповідність макетам презентації (сітка, картка)
- [ ] Тексти без AI-маркерів, термінологія прайсу збережена
- [ ] Мобільний вигляд на реальному телефоні
- [ ] Вибіркова перевірка JSON-LD через Rich Results Test / schema.org validator (2–3 картки)

## 7. Правила автономної сесії

1. Спочатку план у DECISIONS.md, потім код.
1. Кожне відхилення від ТЗ — запис у DECISIONS.md з обґрунтуванням, а не мовчазне рішення.
1. Заборонено: міняти схему/дані (крім статусів draft→published НЕ можна теж — це людське рішення), тягнути CMS/бекенд, додавати позиції.
1. Якщо заблокований (немає фото, неясний токен) — плейсхолдер + запис у DECISIONS.md, рух далі. Не чекати людину.
1. Фінал сесії: чекліст §5–6 з відмітками + git log з осмисленими комітами.
